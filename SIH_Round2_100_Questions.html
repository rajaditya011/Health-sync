HealthSync — Smart India Hackathon Round 2

Complete Defense Q&A (100 Questions)

Team Preparation Document — September 2026 Project: HealthSync — AI-Powered Healthcare Accessibility Platform

SECTION A: TECHNICAL ARCHITECTURE & TECH STACK (Q1–Q15)

Q1. What is the complete tech stack of HealthSync?

A: HealthSync is built on a modern, production-grade web stack:

  • Framework: Next.js 16 (App Router) with React 19 and TypeScript
  • Styling: Tailwind CSS 4 with custom CSS variables for theming
  • 3D Graphics: Three.js + React Three Fiber + Drei for the Digital Twin body model
  • Animations: Framer Motion for page transitions and micro-interactions
  • AI Backend: Groq API (openai/gpt-oss-20b model) for ultra-fast LLM inference
  • OCR Engine: Tesseract.js for on-device medical report text extraction
  • Charts: Recharts for vitals visualization and health trend graphs
  • Icons: Lucide React (575+ medical and UI icons)

Q2. Why did you choose Next.js over other frameworks like React or Angular?

A: Next.js gives us three critical advantages:

  1. Server-side API Routes — All our AI calls (Groq, OCR) happen in /api/ai/* routes on the server. API keys are NEVER exposed to the browser. This is impossible in plain React without a separate backend.
  2. App Router — Lets us build complex role-based layouts (Patient sidebar vs Doctor sidebar vs Hospital admin) with nested layouts and route groups like (app)/ for authenticated pages.
  3. Turbopack — Next.js 16 ships with Turbopack, giving us sub-100ms hot reloads during development, which was critical for our rapid hackathon iteration cycle.

Q3. How does the 3D Digital Twin work technically?

A: The Digital Twin uses React Three Fiber to render a WebGL canvas inside the browser. We define 20+ body parts (Head, Chest, Left Arm, Abdomen, etc.) using primitive geometries — SphereGeometry for joints and CapsuleGeometry for limbs. Each body part is a clickable mesh with:

  • Hover detection — onPointerOver/onPointerOut events scale the part up and change cursor
  • Symptom color mapping — Healthy parts show their default color; Mild symptoms turn yellow (#F59E0B), Moderate turns orange (#F97316), Severe turns red (#EF4444)
  • Holographic shader — A custom MeshPhysicalMaterial with clearcoat, emissive pulsing, and transparency creates the futuristic holographic look
  • Scan ring animation — A torus geometry orbits the body using useFrame for the scanning effect

When a user clicks a body part and selects a severity level, that data is passed to the AI chat context, so the AI knows exactly which areas are affected.

Q4. How many API routes does your backend have and what does each do?

A: We have 6 dedicated AI API routes:

  1. /api/ai/chat — General health conversation with the Digital Twin AI
  2. /api/ai/intake — MediKiosk structured clinical intake using the SOCRATES framework
  3. /api/ai/summarize-intake — Synthesizes the kiosk conversation into a structured Clinical Intake Summary (JSON)
  4. /api/ai/analyze-report — Parses uploaded medical reports (images via OCR, PDFs, text) and returns structured analysis with urgency levels
  5. /api/ai/voice — Voice-based health assistant processing
  6. /api/ai/analyze-appointment — Pre-appointment intelligence gathering

Each route is a Next.js server-side Route Handler — meaning all API keys and AI processing logic stays on the server.

Q5. What AI model are you using and why?

A: We use openai/gpt-oss-20b hosted on the Groq platform. We chose this combination because:

  • Groq's LPU (Language Processing Unit) delivers inference speeds 10-18x faster than traditional GPU-based providers, which is critical for real-time voice conversations and kiosk interactions
  • gpt-oss-20b is an open-source 20-billion parameter reasoning model that supports JSON structured output (response_format: { type: "json_object" }), which is essential for our clinical intake system
  • Cost efficiency — Groq's pricing model is extremely competitive for hackathon-scale usage

Q6. How does the OCR system work for medical reports?

A: Our report analysis pipeline handles three types of uploads:

  1. Text files (.txt, .csv) — Read directly as text using FileReader.readAsText()
  2. PDFs (.pdf) — Extracted server-side using the pdf-parse library which converts PDF binary data to text
  3. Images (.jpg, .png, .webp, .heic) — Converted to base64 on the client, sent to the server, then processed by Tesseract.js (an open-source OCR engine) to extract text from the image

After text extraction, the content is sent to our Groq AI model with a structured prompt that returns a JSON analysis containing: layman summary, technical summary, abnormalities, recommendations, urgency level (Green/Amber/Red), suggested specialist, estimated condition, medication suggestions, follow-up tests, and Jan Aushadhi generic alternatives.

Q7. How do you handle API key rotation and fallback?

A: We implement a dual-key failover system. Our .env.local stores two Groq API keys (GROQ_API_KEY_1 and GROQ_API_KEY_2). Every AI route handler implements a retry loop:

for (let i = 0; i < GROQ_KEYS.length; i++) {
    const response = await fetch(GROQ_ENDPOINT, { Authorization: Bearer ${GROQ_KEYS[i]} });
    data = await response.json();
    if (!data.error) break; // Success — stop retrying
}

If Key 1 hits a rate limit or fails, we automatically fall back to Key 2 with zero user-facing downtime. This pattern can be extended to N keys for production.

Q8. What is the role of the store.ts file?

A: store.ts is the centralized data access layer of HealthSync. It provides 50+ helper functions that abstract all read/write operations. Key functions include:

  • getCurrentUser() / setCurrentUser() — Authentication state
  • getReports() / addReport() — Medical report management
  • getVitals() / addVital() — Vitals data (BP, heart rate, SpO2, etc.)
  • getJourneys() / setJourneys() — Recovery journey management
  • getAppointments() / addAppointment() — Doctor appointment booking
  • saveIntakeSummary() / getIntakeSummaries() — MediKiosk clinical summaries
  • shareReportWithDoctor() / autoShareReportsWithDoctor() — Cross-role data sharing

All data is keyed by user ID (e.g., {userId}_hs_reports) and persisted in localStorage for the prototype. The abstraction layer means we can swap localStorage for PostgreSQL, MongoDB, or Firebase without changing a single UI component.

Q9. How does the real-time data sharing between Patient and Doctor portals work?

A: When a patient uploads a report, the system:

  1. Saves the report via addReport() with all AI analysis data
  2. Calls autoShareReportsWithDoctor() which checks all active appointments
  3. Marks the report's sharedWith array with the doctor's user ID
  4. When the doctor opens their dashboard, getSharedReportsForDoctor() queries all reports where sharedWith includes their ID
  5. The doctor sees the full AI analysis, urgency level, and can add their own clinical notes

We also use the window.addEventListener('storage') event to enable real-time cross-tab synchronization — if the patient uploads a report in Tab A, the doctor dashboard in Tab B updates automatically.

Q10. What is the ai-context.ts module and why is it important?

A: ai-context.ts contains buildAIContext() and formatContextForAI() — two functions that aggregate the patient's complete medical profile before every AI call. The context includes:

  • Current vitals (BP, heart rate, SpO2, temperature, weight)
  • Active medications and prescriptions
  • Recent medical reports and their analyses
  • Active recovery journeys
  • Past appointment history

This context is injected into every AI system prompt, so the AI is always aware of the patient's full medical state. For example, if a patient with diabetes asks about a headache, the AI can correlate it with potential blood sugar fluctuations rather than giving a generic response.

Q11. How is routing and authentication handled?

A: We use Next.js route groups:

  • (app)/ — All authenticated patient pages (dashboard, vitals, reports, digital twin, etc.)
  • doctor-dashboard/ — All doctor-facing pages
  • hospital/, blood-bank/, ayurveda/, admin/ — Administrative portals

Authentication is handled in (app)/layout.tsx which checks getCurrentUser() on every page load. If no user is found, it redirects to /auth. If onboarding is incomplete, it redirects to /onboarding. The doctor dashboard has its own layout.tsx with separate authentication logic checking for doctor-type accounts.

Q12. How do you handle speech recognition and text-to-speech?

A: We use the Web Speech API which is built into modern browsers:

  • Speech Recognition — window.SpeechRecognition or window.webkitSpeechRecognition for voice input. We support both en-IN (English India) and hi-IN (Hindi India) locales.
  • Text-to-Speech — window.speechSynthesis with SpeechSynthesisUtterance for reading AI responses aloud. We strip markdown formatting before speaking and limit to 800 characters for natural speech flow.

In the MediKiosk, voice is the primary input method — the patient speaks, the AI responds, and the system automatically reads the response aloud for a fully hands-free experience.

Q13. What charting/visualization libraries do you use?

A: We use Recharts for all health data visualization:

  • Line charts for vitals trends (blood pressure, heart rate over time)
  • Area charts for SpO2 saturation levels
  • Bar charts for medication adherence tracking
  • Responsive containers that adapt to mobile and desktop screens

All charts use our theming system (CSS variables) so they automatically adjust to light/dark mode.

Q14. How does the MediKiosk structured intake work technically?

A: The Kiosk follows a 6-step pipeline:

  1. START — Welcome screen with language selection
  2. CONSENT — Patient enters ABHA ID (if available) and selects consultation type (Allopathic or AYUSH)
  3. CONVERSE — AI conducts a structured interview using the SOCRATES clinical framework (Site, Onset, Character, Radiation, Associated symptoms, Timing, Exacerbating/relieving factors, Severity). The AI asks ONE question at a time and responds in JSON format with { response, status, redFlagDetected }.
  4. SCAN — Patient uploads documents (prescriptions, lab reports) which are OCR-scanned via Tesseract.js
  5. SUMMARIZE — The /api/ai/summarize-intake route synthesizes the entire conversation and documents into a structured Clinical Intake Summary JSON
  6. COMPLETE — The summary is saved and made available to the doctor's dashboard

SECTION B: DATABASE & DATA MANAGEMENT (Q16–Q25)

Q16. What database are you using?

A: For this hackathon prototype, we use browser localStorage as our persistence layer, abstracted through store.ts. This gives us:

  • Zero setup — No database server needed for the demo
  • Instant reads/writes — Sub-millisecond data access
  • Cross-tab sync — Via the storage event listener
  • Role isolation — Data is keyed by user ID ({userId}_hs_reports, {userId}_hs_vitals, etc.)

For production, the store.ts abstraction can be replaced with any database backend (PostgreSQL, MongoDB, Firebase Firestore) without changing a single UI component, because all data access goes through function calls like getReports() and addReport().

Q17. How would you migrate to a production database?

A: The migration would involve three steps:

  1. Replace store.ts functions — Swap localStorage.getItem() / setItem() calls with database client calls (e.g., Prisma ORM for PostgreSQL, Mongoose for MongoDB)
  2. Add a REST/GraphQL API layer — Move data operations to proper API routes with authentication middleware
  3. Add user authentication — Integrate NextAuth.js or Firebase Auth for proper JWT-based authentication

The key point is that our entire UI layer calls getReports(), not localStorage.getItem('hs_reports'). This abstraction was an intentional architectural decision to make the migration seamless.

Q18. How is patient data organized?

A: Each patient's data is stored in separate namespaced keys:

  • hs_currentUser — Active session user profile (name, email, age, blood group, medical conditions)
  • {userId}_hs_reports — Array of medical reports with AI analyses
  • {userId}_hs_vitals — Array of vitals readings (BP, heart rate, SpO2, temperature, weight)
  • {userId}_hs_journeys — Array of recovery journeys (timeline, medications, diet plans)
  • {userId}_hs_appointments — Array of doctor appointments
  • {userId}_hs_intake_summaries — Array of MediKiosk clinical intake summaries
  • {userId}_hs_digital_twin_chat — Chat history with the Digital Twin AI
  • {userId}_hs_orders — Medicine orders from the pharmacy module

Q19. How does the ABHA database work in your system?

A: We have a simulated ABHA National Database (abhaDb.ts) containing 50 deterministic mock patient records. Each record has:

  • ABHA ID (format: 91-XXXX-XXXX-XXXX)
  • Patient name, phone, email
  • Blood group
  • Medical history (if any)

When a patient enters their ABHA ID at the MediKiosk, the system calls getPatientByAbhaId() to retrieve their pre-existing records. This data is then injected into the AI intake prompt so the AI can say things like "I see from your ABHA records that you have a history of Type 2 Diabetes. Is that still being managed?" — creating a personalized, context-aware experience.

In production, this would connect to the actual ABDM (Ayushman Bharat Digital Mission) APIs.

Q20. How do you handle data consistency across the Patient and Doctor portals?

A: Both portals read from the same underlying data store. When a patient adds a report or books an appointment:

  1. The data is saved with the patient's user ID
  2. The sharedWith field links it to the doctor's user ID
  3. The doctor's dashboard queries all data where their ID appears in sharedWith

We also use the window.addEventListener('storage') event to detect cross-tab changes, so if the patient uploads a report while the doctor dashboard is open in another tab, the doctor sees it immediately.

Q21. What is the data model for a Medical Report?

A: Each report follows this TypeScript interface:

interface MedicalReport {
    id: string;
    userId: string;
    fileName: string;
    uploadDate: string;
    fileData: string;           // First 5000 chars of content
    aiSummary: string;          // Layman explanation
    technicalSummary: string;   // Doctor-facing summary
    abnormalities: string[];    // List of abnormal findings
    recommendations: string[];  // Action items
    urgencyLevel: 'green' | 'amber' | 'red';
    fileType: string;
    category: string;           // prescriptions | laboratory | discharge | imaging | other
    sharedWith: string[];       // Doctor IDs
}

Q22. How do you prevent data loss or corruption?

A: Multiple safeguards:

  1. Atomic writes — Each setItem() call writes the full array, not individual items
  2. Try-catch wrappers — All localStorage operations are wrapped in try-catch blocks
  3. Data validation — AI responses are parsed with fallback JSON extraction (text.match(/\{[\s\S]*\}/)) to handle malformed responses
  4. ID generation — Every record uses generateId() which creates unique IDs using Date.now().toString(36) + Math.random().toString(36)

Q24. How much data can the system handle?

A: localStorage has a ~5MB limit per origin. For our prototype, this comfortably handles:

  • 100+ medical reports
  • 1000+ vitals readings
  • 50+ appointments
  • 50+ chat sessions

For production, moving to a cloud database removes this limit entirely. Our store.ts abstraction ensures this migration requires zero UI changes.

Q25. How do you handle the 50 mock ABHA patients?

A: The abhaDb.ts file generates 50 deterministic patient records using a seeded pseudo-random function (Math.sin(seed)) to ensure Server-Side Rendering (SSR) and Client-Side Rendering (CSR) produce identical data (preventing React hydration mismatches). The data includes realistic Indian names, phone numbers, blood groups, and medical conditions. Any edits made through the ABHA Gov portal are persisted to localStorage under the abhaDatabase_v1 key.

SECTION C: SECURITY & PRIVACY (Q26–Q35)

Q26. How do you protect API keys?

A: All API keys are stored in .env.local (which is gitignored) and accessed only in server-side API routes (/api/ai/*). These routes run in Node.js on the server — the browser never sees, downloads, or has access to any API key. This is a fundamental security advantage of Next.js server-side routes over client-side React apps.

Q27. Is patient data encrypted?

A: In the current prototype, data is stored in localStorage which is sandboxed by the browser's Same-Origin Policy — no other website can access it. For production:

  1. In transit — All communication would be over HTTPS/TLS 1.3
  2. At rest — Database encryption (AES-256) for all patient records
  3. Field-level encryption — Sensitive fields like ABHA ID, medical history, and prescriptions would be individually encrypted

Q28. How do you handle HIPAA/DISHA compliance?

A: For the Indian healthcare context, the relevant framework is DISHA (Digital Information Security in Healthcare Act) and the ABDM guidelines. Our architecture supports compliance through:

  1. Role-Based Access Control (RBAC) — Patients see only their data; doctors see only data shared with them; admins see aggregate metrics only
  2. Audit trails — Every report upload, share action, and AI interaction is timestamped
  3. Data minimization — We store only the first 5000 characters of report content, not the full file
  4. Consent-based sharing — Reports are shared with doctors only after the patient has booked an appointment or explicitly shared

Q29. Can the AI be manipulated to give dangerous medical advice?

A: We have multiple safeguards:

  1. System prompt guardrails — Every AI route includes strict instructions: "NEVER diagnose. Use phrases like 'these results may suggest' or 'your doctor should evaluate'"
  2. Urgency escalation — If the AI detects red-flag symptoms (chest pain, difficulty breathing, stroke signs), it immediately recommends emergency care
  3. Disclaimer injection — Every AI analysis includes a mandatory disclaimer that it must be verified by a qualified healthcare provider
  4. Triage-only design — The AI provides urgency levels (Green/Amber/Red) and recommendations, never prescriptions or diagnoses

Q30. How do you prevent unauthorized access to the Doctor Dashboard?

A: The Doctor Dashboard has its own layout.tsx with authentication checks. It verifies that the current user has a role: 'doctor' flag. The registration flow for doctors includes a separate "Sign Up as Doctor" path that captures specialty, license number, and hospital affiliation. Patient accounts cannot access doctor routes and vice versa.

Q31. What happens to patient data if the browser cache is cleared?

A: In the current prototype, data is lost if localStorage is cleared — this is a known limitation of the hackathon version. In production, all data would be in a cloud database, and localStorage would only serve as a local cache for offline access. The transition requires changing only the store.ts file, not any UI code.

Q32. How do you handle cross-site scripting (XSS) attacks?

A: React's JSX automatically escapes all rendered content, preventing XSS by default. We do not use dangerouslySetInnerHTML anywhere in the codebase. All user inputs (chat messages, ABHA IDs, report text) are passed as string values, never injected as HTML.

Q33. How do you protect the AI from prompt injection attacks?

A: Our system prompts are server-side only and include strict output format requirements (JSON schema). Even if a malicious user tries to inject instructions via chat, the AI is constrained to respond only within the defined JSON structure (e.g., { "response": "...", "status": "IN_PROGRESS", "redFlagDetected": false }). Any response that doesn't match the expected schema is caught by our JSON parsing fallback.

Q34. Is the ABHA data in your system real?

A: No. Our ABHA database contains 50 completely synthetic/mock patient records generated algorithmically. No real patient data is used anywhere in the system. The ABHA IDs follow the standard format (91-XXXX-XXXX-XXXX) but are fictional. In production, we would integrate with the real ABDM Health Information Exchange (HIE) APIs.

Q35. How would you handle multi-hospital deployments securely?

A: Each hospital would get its own tenant in a multi-tenant architecture:

  1. Database isolation — Separate schemas or databases per hospital
  2. API key management — Each hospital gets unique API credentials
  3. Network segmentation — Hospital data stays within their VPC
  4. SSO integration — Doctors authenticate via their hospital's existing identity provider

SECTION D: USP & INNOVATION (Q36–Q50)

Q36. What is the USP of HealthSync?

A: "Visually intuitive, AI-driven healthcare accessibility." We remove the medical literacy barrier. Our three-pillar USP:

  1. 3D Digital Twin — Patients visually interact with a body model to pinpoint symptoms instead of typing complex medical terms
  2. AI Report Demystification — Lab reports are converted from medical jargon to simple language, with Jan Aushadhi (generic) medicine alternatives
  3. MediKiosk — A self-service clinical intake system for hospital waiting rooms that can work without a doctor present

Q37. How is HealthSync different from Practo, 1mg, or other health apps?

A: Existing apps are digital forms and video call wrappers. HealthSync fundamentally changes HOW patients interact with healthcare:

  • Practo — Primarily a doctor discovery and appointment booking platform. No AI intake, no report analysis, no 3D visualization.
  • 1mg — An online pharmacy with basic symptom checkers. No structured clinical intake, no doctor dashboard integration.
  • HealthSync — An end-to-end ecosystem: Patient AI intake → Structured clinical data → Doctor dashboard → Hospital administration → Blood bank → AYUSH ministry — all connected in one platform.

Q38. What makes the MediKiosk unique?

A: The MediKiosk is designed for Indian hospital waiting rooms where:

  • Patients wait 2-4 hours before seeing a doctor
  • Patients struggle to articulate symptoms in medical terminology
  • Doctors spend 60% of consultation time just gathering basic history

Our Kiosk solves all three problems. While the patient waits, the AI conducts a structured SOCRATES-based clinical intake via voice. By the time the doctor sees them, a complete Clinical Intake Summary is ready — saving 10-15 minutes per consultation. Multiply that by 100 patients/day = 25 extra hours of doctor productivity per day.

Q39. How does the Jan Aushadhi feature work?

A: When the AI analyzes a medical report and finds prescribed medicines, it automatically suggests generic alternatives available at Jan Aushadhi Kendras (government-run generic medicine stores). For example, if the report shows "Tab Crestor 10mg (₹850/month)", the AI suggests "Generic Rosuvastatin 10mg (₹45/month) available at Jan Aushadhi Kendra." This directly addresses the socio-economic aspect of healthcare accessibility.

Q40. Why did you build a 3D model instead of using a simple body diagram?

A: A 2D diagram is static and cannot show:

  1. Depth — Back pain vs. chest pain requires rotating the model
  2. Interactive feedback — Our model pulses and changes color in real-time based on selected severity
  3. Engagement — The holographic look creates a "wow" factor that makes patients want to interact with it, reducing the barrier to reporting symptoms
  4. Extensibility — We can add organ-level zoom, X-ray overlay views, and AR integration in the future

Q41. How does the Emergency SOS system work?

A: The Emergency page provides one-tap access to:

  1. Ambulance booking — Dispatches based on user's location
  2. Hospital calling — Connects to the nearest emergency room
  3. Family alerting — Sends emergency notifications to registered family members
  4. Blood request — Sends urgent blood type requests to the Blood Bank Portal
  5. Bed booking — Reserves ICU/Ward/General beds at the nearest hospital
  6. Machine booking — Requests MRI, CT Scanner, X-Ray, or Ultrasound slots

Each action generates a cross-portal request that appears in the Hospital Administration Portal for immediate processing.

Q42. How does the recovery journey system work?

A: After a report analysis, the AI can generate a complete Recovery Journey containing:

  • Timeline — Day-by-day recovery steps (checkups, medication changes, exercises, lifestyle modifications)
  • Medication schedule — With dosage, frequency, and time-based reminders
  • Diet plan — Personalized Indian dietary recommendations (Breakfast/Lunch/Snack/Dinner) with calorie counts
  • Progress tracking — Each step can be marked as pending/in-progress/completed
  • Doctor notes — The assigned doctor can add clinical notes and modify the plan

Q43. Can the system work in multiple languages?

A: Yes. We have built a translation system (translations.ts) with LanguageProvider context that supports English and Hindi. All navigation labels, button text, and system messages go through the t() translation function. The Voice AI also supports both en-IN and hi-IN locales for speech recognition and text-to-speech.

Q44. How does the Doctor Dashboard add value?

A: The Doctor Dashboard provides:

  1. Pre-visit intelligence — Before the patient walks in, the doctor sees their complete AI-generated intake summary, uploaded reports, vitals history, and active medications
  2. Structured data — Instead of handwritten notes, doctors get machine-readable JSON with Chief Complaint, HPI (SOCRATES), Past Medical History, Drug/Allergy History, and Review of Systems
  3. Quick prescriptions — Doctors can write digital prescriptions that automatically appear in the patient's app
  4. Patient management — A centralized list of all assigned patients with their triage levels

Q45. What is unique about your report analysis compared to Google Health or similar tools?

A: Three things:

  1. Fake report detection — Our AI flags non-genuine reports (gibberish, lorem ipsum, non-medical content) with isFake: true
  2. Dual summary — We generate BOTH a layman summary (for the patient) and a technical summary (for the doctor) from the same report
  3. Actionable output — We don't just summarize; we generate urgency levels, specialist recommendations, follow-up tests, AND a complete recovery journey — all from a single report upload

Q46. How does the Blood Bank Portal work?

A: The Blood Bank Portal shows:

  • Live inventory — Real-time counts of all 8 blood types (A±, B±, O±, AB±) with location information
  • Critical alerts — Types with fewer than 10 units are highlighted in red
  • Emergency requests — When a patient uses the Emergency SOS to request blood, it appears as a real-time notification in the Blood Bank Portal
  • Stock management — Administrators can edit inventory counts (add/remove units)

Q47. How does the Hospital Administration Portal work?

A: The Hospital Portal provides:

  • Room availability — ICU, Normal Ward, General Ward with occupancy percentages and visual progress bars
  • Machine status — MRI, CT Scanner, X-Ray, Ultrasound availability tracking
  • Bed requests — Emergency bed booking requests from patients
  • Pharmacy orders — Medicine order processing and status management
  • Doctor roster — All active doctors with their specialties and current availability

Q48. What is the Admin Command Center?

A: The Admin Command Center (/admin) provides a god-view of the entire ecosystem:

  • ABHA Network statistics (registered patients)
  • MediKiosk logs (total AI intake summaries generated)
  • Blood Bank total units
  • Hospital occupancy percentage
  • System health monitor — showing ONLINE/OFFLINE status of all subsystems (ABHA API, MediKiosk Voice Processing, Blood Bank DB, Hospital Management System)

Q49. How does cross-portal data flow work?

A: HealthSync is a connected ecosystem, not isolated modules:

Patient (Emergency SOS) → Blood Bank (receives blood request)
Patient (Emergency SOS) → Hospital (receives bed/machine request)
Patient (MediKiosk Intake) → Doctor Dashboard (receives clinical summary)
Patient (Report Upload) → Doctor Dashboard (auto-shared report)
Patient (Medicine Order) → Hospital Pharmacy (receives order)
Doctor (Prescription) → Patient App (receives prescription)
AYUSH Doctor (Consultation) → Ayush Dashboard (aggregated analytics)

Q50. What makes your AI intake different from a simple chatbot?

A: Our AI is clinically trained to follow the SOCRATES framework used by real doctors:

  • Site — Where exactly is the problem?
  • Onset — When did it start?
  • Character — What does it feel like?
  • Radiation — Does it spread anywhere?
  • Associated symptoms — Any other symptoms?
  • Time course — Is it getting better or worse?
  • Exacerbating/relieving factors — What makes it better or worse?
  • Severity — On a scale of 1-10?

It asks ONE question at a time, detects red-flag emergencies, and produces a medically structured output — not a casual chat transcript.

SECTION E: GOVERNMENT TERMS & AYUSH/ABHA INTEGRATION (Q51–Q70)

Q51. What is ABHA?

A: ABHA stands for Ayushman Bharat Health Account. It is a 14-digit unique health ID issued by the Government of India under the Ayushman Bharat Digital Mission (ABDM). It serves as a universal health identifier that links all of a patient's health records across hospitals, clinics, and diagnostic centers. In our app, patients enter their ABHA ID at the MediKiosk to pull their pre-existing medical history.

Q52. What is ABDM?

A: ABDM stands for Ayushman Bharat Digital Mission. It is the Government of India's flagship initiative to create a unified digital health infrastructure. It includes:

  1. ABHA — Health Account (unique ID)
  2. Health Information Exchange (HIE) — For sharing records between providers
  3. Health Facility Registry (HFR) — Database of all registered healthcare facilities
  4. Healthcare Professionals Registry (HPR) — Database of all registered healthcare providers
  5. Unified Health Interface (UHI) — Open protocol for health services

Our app integrates with the ABHA component and simulates the HIE for seamless data exchange.

Q53. What is AYUSH?

A: AYUSH stands for Ayurveda, Yoga & Naturopathy, Unani, Siddha, and Homeopathy. It is the Ministry of AYUSH under the Government of India that promotes and regulates traditional Indian medicine systems. In HealthSync, we have:

  1. AYUSH consultation type in the MediKiosk — When selected, the AI also assesses Prakriti, Vikriti, Agni, and Ahara-Vihara
  2. Ayurvedic doctors on the platform — With specialties like Panchakarma, Ayurvedic Physician, etc.
  3. Ayush Ministry Dashboard — An admin portal showing consultations, medicine inventory, and active Vaidyas

Q54. What is Prakriti?

A: Prakriti refers to a person's innate body constitution in Ayurveda. It is determined at birth and remains constant throughout life. There are three main doshas:

  1. Vata — Air + Space (thin build, creative, anxious)
  2. Pitta — Fire + Water (medium build, sharp intellect, prone to inflammation)
  3. Kapha — Earth + Water (heavy build, calm, prone to congestion)

Most people are a combination (e.g., Vata-Pitta). In our app, when AYUSH consultation is selected, the AI assesses the patient's Prakriti through targeted questions about body type, digestion, sleep patterns, and temperament.

Q55. What is Vikriti?

A: Vikriti refers to the current state of imbalance of the doshas. While Prakriti is your natural constitution, Vikriti tells you which dosha is currently aggravated. For example, a Vata-Pitta person might have Pitta Vikriti (Pitta is currently elevated) due to stress, spicy food, or hot weather. Our AI assesses Vikriti by asking about current symptoms, recent dietary changes, and lifestyle factors.

Q56. What is Agni in Ayurveda?

A: Agni is the digestive fire in Ayurveda. It governs digestion, metabolism, and the body's ability to process food and experiences. There are four types:

  1. Sama Agni — Balanced digestion (healthy)
  2. Vishama Agni — Irregular digestion (Vata imbalance)
  3. Tikshna Agni — Hyperactive digestion (Pitta imbalance)
  4. Manda Agni — Slow digestion (Kapha imbalance)

Our AI assesses Agni by asking about appetite patterns, digestion quality, bloating, and bowel habits.

Q57. What is Ahara-Vihara?

A: Ahara-Vihara means diet and lifestyle:

  • Ahara (Diet) — What you eat, when you eat, how you eat
  • Vihara (Lifestyle) — Sleep patterns, exercise habits, daily routine, stress levels

In Ayurveda, Ahara-Vihara is considered the primary cause of most diseases. Our AI captures this information to provide personalized dietary and lifestyle recommendations based on the patient's Prakriti and current Vikriti.

Q58. What is Panchakarma?

A: Panchakarma is a set of five Ayurvedic detoxification therapies:

  1. Vamana — Therapeutic vomiting (for Kapha disorders)
  2. Virechana — Purgation therapy (for Pitta disorders)
  3. Basti — Medicated enema (for Vata disorders)
  4. Nasya — Nasal medication (for head/neck disorders)
  5. Raktamokshana — Blood purification

We have a Panchakarma Specialist (Dr. Smita Naram) on our platform, and the Ayush Dashboard tracks all Panchakarma-related consultations.

Q59. What is the National AYUSH Mission (NAM)?

A: NAM is a Government of India centrally sponsored scheme for promoting AYUSH systems through:

  • Cost-effective AYUSH services
  • Strengthening educational institutions
  • Quality control of AYUSH drugs
  • Medicinal plant cultivation

Our Ayush Ministry Dashboard supports NAM objectives by providing digital tracking of Ayurvedic consultations, medicine dispensation, and practitioner activity.

Q60. How do you integrate AYUSH with Allopathic treatment in your app?

A: We use a unified doctor listing that includes both Allopathic and Ayurvedic practitioners:

  • 18 Allopathic doctors (Cardiologist, Nephrologist, Neurologist, etc.)
  • 5 Ayurvedic/AYUSH doctors (Ayurvedic Physician, Panchakarma Specialist, Homeopath, etc.)
  • 2 Homeopathic practitioners

Patients can choose their consultation type at the MediKiosk. If they choose AYUSH, the AI intake additionally assesses Prakriti, Vikriti, Agni, and Ahara-Vihara. The same Clinical Intake Summary is shared with the assigned AYUSH doctor through the Doctor Dashboard.

Q61. What are Jan Aushadhi Kendras?

A: Pradhan Mantri Bhartiya Janaushadhi Pariyojana (PMBJP) is a government campaign to provide quality generic medicines at affordable prices through dedicated stores called Jan Aushadhi Kendras. These stores sell medicines at 50-90% less than branded equivalents. Our AI report analysis automatically suggests Jan Aushadhi alternatives for every branded medicine found in reports.

Q62. What is the SOCRATES framework mentioned in your app?

A: SOCRATES is a clinical mnemonic used by doctors worldwide to take a structured history of a presenting complaint:

  • S — Site (Where is the problem?)
  • O — Onset (When did it start? Sudden or gradual?)
  • C — Character (What does the pain/symptom feel like?)
  • R — Radiation (Does it spread to other areas?)
  • A — Associated symptoms (Any other symptoms?)
  • T — Time course (Constant or intermittent? Getting better or worse?)
  • E — Exacerbating/relieving factors (What makes it worse/better?)
  • S — Severity (Scale of 1-10?)

Our MediKiosk AI follows this framework systematically to ensure no critical information is missed.

Q63. What is the Ayushman Bharat scheme?

A: Ayushman Bharat is the Government of India's flagship healthcare program with two components:

  1. Health and Wellness Centers (HWCs) — 150,000 primary health centers providing free essential services
  2. Pradhan Mantri Jan Arogya Yojana (PM-JAY) — Health insurance covering ₹5 lakh per family per year for secondary and tertiary hospitalization

ABHA (our integrated health ID) is part of the Ayushman Bharat ecosystem.

  3. Active Vaidyas — Number of Ayurvedic practitioners actively seeing patients
  4. Inventory management — Real-time stock tracking with price information
  5. Consultation timeline — Chronological view of all AYUSH appointments

Q65. What Ayurvedic medicines does your platform track?

  3. Giloy Ghanvati — Immunity booster (₹70)
  4. Brahmi Vati — Brain and memory tonic (₹90)
  5. Chyawanprash — General health supplement (₹150)

Q66. What is Vaidya?

A: Vaidya is the Sanskrit term for a practitioner of Ayurvedic medicine, equivalent to "Doctor" in Allopathic medicine. Our platform lists Vaidyas (Ayurvedic doctors) alongside Allopathic doctors, allowing patients to choose their preferred system of medicine.

Q67. How do you handle the ABHA ID format?

The 91 prefix represents the India country code. In production, ABHA IDs would be fetched from the ABDM APIs using the patient's Aadhaar or mobile number.

Q92. How do you handle AI hallucinations in a medical context?

A: Five-layer defense:

  1. System prompt constraints — "NEVER diagnose. Use 'may suggest' language"
  2. Structured JSON output — Forces the AI to fill specific fields rather than free-form text
  3. Temperature control — Set to 0.2-0.3 (low creativity, high factuality) for all medical routes
  4. Output validation — JSON parsing with schema checks catches malformed responses
  5. Human-in-the-loop — Every AI analysis includes "Must be verified by a qualified healthcare provider"
